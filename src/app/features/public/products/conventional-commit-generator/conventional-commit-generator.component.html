What is a Conventional Commit? (v1.0.0 Specification)

The Conventional Commits specification is a lightweight, standardized convention established on top of Git commit messages. It introduces an explicit, machine-readable syntax that makes Git histories cleaner, easier to navigate, and fully compatible with automated versioning systems such as Semantic Versioning (SemVer).

Conventional Commit Structure
<type>[optional scope][!]: <description in imperative mood>
[optional blank line]
[optional body: detailed explanation of motivation and changes]
[optional blank line]
[optional footer(s): BREAKING CHANGE: <note> or Refs #123 / Fixes #42]

How the 4-Stage Analysis Pipeline Works

When you paste raw, casual text into our generator, it passes through four discrete linguistic processing stages to produce clean, compliant commits:

01

Type Detection

Evaluates keywords to identify commit intent: fix for bug resolutions, feat for new features, refactor for architectural updates, and build for package upgrades.

02

Scope Extraction

Detects architectural boundaries like auth, api, checkout, ui, or deps from natural language context ("in login page", "for API", file paths).

03

Imperative Titles

Converts past tense verbs to imperative mood ("fixed" → "fix", "added" → "add"), removes filler words, and enforces the standard 50-character limit.

04

Body & Footers

Re-wraps long descriptions at 72 characters, flags breaking changes with ! and BREAKING CHANGE:, and isolates issue numbers.
